# Wiki 與 Skill 維護節奏

手動流程，不建立背景排程。使用 llm-wiki 與 skill-evolution；
course/sources/ 的 RedCap 指令僅是歷史案例。

| 時機 | 動作 | 產物／條件 |
|---|---|---|
| 任務執行 | 保留命令、版本、輸出與可觀察結果 | 原始證據，不收集隱藏推理或憑證 |
| 完整 workflow 結案 | 詢問是否整理 Wiki | 同意後才 capture |
| 每次 Wiki 更新 | 自動 skill-evolution assess | 維護／無需修改／證據不足／候選 |
| 維護問題已確認 | 修復路徑、連結、命令筆誤並驗證 | 不等兩次事件，不擴大副作用 |
| 品質候選有資格 | 保留原版與隔離候選、先訂驗證条件 | 同根因兩次、成功／失敗證據、WIP = 1 |
| 有適用專案任務 | 以實際 interface 比較兩版 | 同版本兩個不同任務，至少一個未用於撰寫 |
| 候選穩定 | 呈現差異、結果、指定目標及回退來源 | 使用者決定啟用 |
| 評估／拒絕／啟用後 | 回寫同一 Wiki 演進紀錄 | 保留歷史，回饋不再觸發評估 |

正確性與完整性優先，時間／token 為次要指標；未量測為未知。
候選改版後舊紀錄不能證明新版本穩定。兩個本機任務通過支持推廣建議，
不代表跨專案普遍有效。

每週可按需要 llm-wiki lint，報告失效來源與矛盾後再做有界更新；
不因到了時間就產生候選、提升 confirmed 或啟用 Skill。
