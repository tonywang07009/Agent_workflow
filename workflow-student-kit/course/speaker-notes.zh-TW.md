# Workflow 90 分鐘講者教案

8 段时间與課程卡一致；現行指引以 skills 為準，來源快照作歷史對照。

## 00–08｜先看整張地圖

目標：能用一句話區分 Skill、MCP、OpenSpec 與 Wiki。

- 0–2 分：用「資源不足時不得發送」介紹貫穿案例，這是教學假設而非已完成實驗。
- 2–5 分：四個名詞各給一個檔案或操作例子。
- 5–8 分：沿主線走一遍，讓學員用自己的話重述。

示範：點選上方三段流程圖，指出專案工具設定、change 停點，以及 Wiki 回饋如何接回 Skill 改進。

提問：安裝更多 MCP，會自動得到更好的規格嗎？

參考答案：不會。需求與驗收仍由人與 OpenSpec 決定；工具只提供可用能力。

停止條件：只看進度不開始實作；已提供的工具連結不代表工具目前可用。

## 08–18｜釐清需求與驗收

目標：把模糊需求改寫成可觀察的成功與拒絕條件。

- 前 3 分：示範把形容詞改成可觀察行為。
- 中間 4 分：學員寫一條 Given／When／Then。
- 最後 3 分：抽一組答案，加入剛好等於與負值反例。

示範：練習一（4 分鐘）：將「讓排程更穩定」改成一條可測需求。兩人互問：要觀察哪個輸出才算完成？

提問：「不 crash」能證明拒絕後沒有發送嗎？

參考答案：不能，需要觀察 send 計數或同一 interface 下的可見副作用。

停止條件：不知道資源單位或拒絕副作用時，先補定義；不自行替使用者決定。

## 18–30｜領域語言與深 module

目標：說明 interface 的義務，並判斷新抽象是否必要。

- 前 4 分：以資源單位示範領域詞彙與實作參數的不同。
- 中間 5 分：畫 before／after，讓學員用 deletion test 挑戰新 wrapper。
- 最後 3 分：說明只在真實架構摩擦時使用 improve-codebase-architecture。

示範：比較：每個 caller 自行檢查再發送；與既有 admission module 同時負責判定和拒絕結果。圈出測試入口與 state owner。

提問：把所有函式縮成一行，module 就更 deep 嗎？

參考答案：不是。深度取決於 interface 的能力與認知負擔，而不是程式行數比例。

停止條件：未找到 owner 就不另建平行實作；既有設計足夠就停止架構掃描。

## 30–42｜寫規格時就帶入架構

目標：知道四種 artifact 的責任與依賴順序。

- 前 4 分：四份文件各看一個短段落。
- 中間 5 分：請學員把「回傳拒絕」與「不產生發送副作用」分開列驗收。
- 最後 3 分：講 CLI 動態路徑；下載包不保證各版本都有本專案延伸欄位。

示範：只讀示範：openspec list --json。挑一個既有 change，對照 proposal、design、specs、tasks 各回答哪個問題。

提問：將 send_count = 0 只寫在 tasks，漏在 specs，可以嗎？

參考答案：會失去行為要求的權威來源。先在 specs 定義，再讓 tasks 連到檢查。

停止條件：需求或驗收改變時回到 OpenSpec；不得從勾選完成推論 runtime 成功。

## 42–52｜依問題選擇工具

目標：正確區分 MCP、CLI、文件與實際權限。

- 前 3 分：畫 host → client → server → resource／tool；補一條 shell → CLI。
- 中間 4 分：以 caller／diff／PDF／結果發布四種題目分組選工具。
- 最後 3 分：示範讀到來源路徑仍不等於證明 runtime apply。

示範：比較「修正記帳功能」與「整理研究文件」：各自需要哪些能力，哪些工具不必啟動？

提問：工具出現在安裝清單中，是否代表本次可以直接使用？

參考答案：不代表。仍須確認實際介面、安裝與存取狀態，以及它是否能提供本任務所需證據。

停止條件：不執行未填妥的範本命令，不複製他人機器的健康狀態與絕對路徑。

## 52–65｜TDD、審查與證據階梯

目標：分清 RED、GREEN、review 與 runtime outcome。

- 前 4 分：口述有效 RED 與環境失敗差異。
- 中間 5 分：討論 no-send-on-refusal 與測試穿過同一 interface。
- 最後 4 分：用假想 trace 練習證據分級，說明 archive 前提。

示範：展示假想 trace：request accepted、E2 ACK、缺少 gNB apply marker。請學員為「控制成功」投 PASS／PARTIAL／BLOCKED。這是判讀練習，不是假造 runtime log。

提問：收到 ACK，就可以寫「UE 效能改善」嗎？

參考答案：不可以，還需要接受、套用與效果指標；這三種證據不能互相替代。

停止條件：缺 apply marker 不能報控制套用成功；測試不足回 TDD，驗收改變回 OpenSpec。

## 65–80｜LLM Wiki 與品質評估

目標：說明論文機制與本專案採用範圍，拒絕無證據自動演進。

- 前 4 分：介紹論文三層與四步，不講未在本專案量測的提升百分比。
- 中間 6 分：逐項對照論文與人審版限制，澄清 Water Spider 是本專案角色。
- 最後 5 分：講 context packet、status／evidence_tier 與資料夾導航。

示範：比較兩個案例：修正封存路徑；改善 Agent 經常漏掉拒絕情境的行為。指出哪個直接維護、哪個需要候選。

提問：每次 Wiki 更新是否都必須修改 Skill？

參考答案：不必。每次更新都評估；證據不足或沒有改進必要也是有效結果。維護修復則另按已確認意圖直接處理。

停止條件：Wiki 同意不代表 Skill 啟用；來源不足不宣稱成功。回饋紀錄不再次觸發遞迴評估。

## 80–90｜局部驗證，再決定推廣

目標：完成一次候選拒絕判斷，知道下載包如何使用。

- 前 4 分：區分 Wiki 知識與 active skill，說明候選的隔離位置。
- 中間 5 分：比較兩個不同任務與一次重跑，討論版本變更後為何重驗。
- 最後 3 分：展示 management/ 範本、$workflow 啟動提示與本機先驗證的回家作業。

示範：練習：候選通過同一任務兩次，另一個新任務卻漏了拒絕情境。判斷能否建議推廣。

提問：候選格式檢查通過，就可以更新共用 Skill 嗎？

參考答案：不行。還需不同任務的實際品質證據、沒有必要驗收退步，以及使用者對指定版本與目標的啟用決定。

停止條件：結構檢查不證明 Agent 品質；兩次同任務不算兩個任務，候選不能自行降低啟用門檻。
